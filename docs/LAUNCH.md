# Чек-лист первого запуска

Порядок важен: панель и бот пишут в одну БД, а расписание должно появиться
раньше, чем на него кто-то подпишется.

## 1. Подготовка окружения

- [ ] Проект развёрнут в `/opt/vkbot` (или поправлены пути в `deploy/*.service`).
- [ ] `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`
- [ ] `cp .env.example .env`, заполнены `VK_TOKEN`, `ADMIN_ID`, `PANEL_SECRET`.
- [ ] `PANEL_SECRET` — случайные 64 hex-символа, не переиспользован откуда-то ещё.
      Его смена разлогинивает всех.
- [ ] `ADMIN_ID` одинаков для бота и панели (не разводите `ADMIN_ID` и `ADMIN_VK_ID`).
- [ ] В `ADMIN_VK_IDS` вписан запасной владелец (второй ваш аккаунт или доверенный
      человек). Владельцы из env — единственные, кого не снять через панель; если
      он один и доступ к тому VK потерян, вернуть владение можно только с сервера.
- [ ] Проверено, что панель не стартует без владельца: убрать `ADMIN_ID` →
      `FATAL: не задан ни один владелец панели` → вернуть обратно.
- [ ] `PANEL_BASE_URL` начинается с `https://`, если панель за TLS — от этого
      зависят Secure-куки, `SameSite=None` для VK Mini App и HSTS.
- [ ] `PANEL_TRUSTED_PROXIES=1` при работе за nginx, `0` при прямом доступе.
- [ ] `UPLOAD_API_TOKEN` задан, если планируется загрузка расписания через REST.
      Пусто = API отвечает 401 на всё, это нормально.
- [ ] Права на `.env`: `chmod 600 .env`.
- [ ] Часовой пояс сервера менять не обязательно: приложение пишет все отметки
      времени в МСК само (`config.now_msk()`), от системного пояса не зависит.

## 1а. Часовой пояс и данные

- [ ] `timedatectl set-timezone Europe/Moscow`. Предметная логика считает время
      через `now_msk()`, но журнал аудита, коды входа, `last_seen` и метки версий
      расписания пишутся временем сервера. На UTC-сервере `/admin/audit` разойдётся
      с расписанием на три часа.
- [ ] Перенесены боевые данные, если бот уже работал: `notes.db`, `sсhedule.db`
      (буква `с` кириллическая) и каталог `schedule_versions/` — без последнего
      не работает откат расписания.
- [ ] Владелец файлов — пользователь, под которым идут сервисы; каталог проекта
      доступен ему на запись (`ReadWritePaths=/opt/vkbot` в юнитах).

## 2. Сеть и TLS

- [ ] `PANEL_HOST=127.0.0.1` — панель не смотрит в интернет напрямую.
- [ ] nginx поднят по `deploy/nginx-panel.conf`, `nginx -t` проходит.
- [ ] Сертификат выпущен (`certbot --nginx -d <домен>`), автопродление активно.
- [ ] `client_max_body_size` в nginx не меньше `PANEL_MAX_UPLOAD_MB`.
- [ ] Порт 5000 закрыт извне (`ufw status` / firewall провайдера).

## 3. Запуск сервисов

- [ ] `systemctl enable --now vkbot vkpanel`
- [ ] `systemctl status vkbot vkpanel` — оба `active (running)`.
- [ ] `journalctl -u vkbot -n 50` — есть `VK bot is starting...`, нет трейсбеков.
- [ ] Панель отвечает: `curl -I https://<домен>/login` → 200.

## 4. Первое расписание

- [ ] В боте «🔑 Войти в панель» выдаёт код, код принимается на `/login`.
- [ ] Загружен реальный `.xlsx`, дифф на превью выглядит осмысленно
      (число записей и список направлений совпадают с ожиданием).
- [ ] «Применить» завершилось без ошибки, запись появилась в `/admin/audit`
      (действие `schedule.upload`).
- [ ] `/schedule` показывает пары, у пар по чётным/нечётным неделям стоят метки
      `чёт` / `нечет`.
- [ ] `/admin/conflicts` просмотрен: накладки преподавателей и аудиторий — это
      обычно ошибки в исходном файле, а не в импорте.

## 5. Проверка бота глазами студента

С отдельного аккаунта (не owner):

- [ ] «Начать» → главное меню отвечает.
- [ ] «Расписание» → курс → направление → день: пары совпадают с панелью,
      чётность недели совпадает с плашкой в панели.
- [ ] Заметка создаётся и удаляется по номеру.
- [ ] Напоминание на +2 минуты приходит вовремя.
- [ ] Дедлайн создаётся; в списке видно, сколько осталось.
- [ ] Подписка на пары оформляется и видна в `/admin/users`.
- [ ] **Уведомление о паре приходит только на текущую неделю.** Если пара помечена
      `*`/`**` в Excel — на «чужой» неделе пуша быть не должно.

## 5а. Передача владения

- [ ] «Управление админами» показывает владельцев с пометкой источника:
      `из .env` (снимается только на сервере) и `выдан в панели`.
- [ ] Передача владения без кода не проходит, с кодом из бота — проходит.
- [ ] Событие видно в `/admin/audit` (`admin.owner_grant`) и пришло уведомлением
      в VK всем владельцам.
- [ ] Снятие владения оставляет человеку права админа.

## 6. Рассылка

- [ ] Тестовая рассылка на себе: `/admin/broadcast`, счётчик «отправлено» растёт,
      статус доходит до `завершена`.
- [ ] Понятно, что отмены после старта нет: текст перечитан перед отправкой.

## 7. Бэкапы

- [ ] Установлен таймер: `cp deploy/vkbot-backup.{service,timer} /etc/systemd/system/`,
      `systemctl daemon-reload && systemctl enable --now vkbot-backup.timer`.
- [ ] **Пути в юните поправлены под каталог установки.** В репозитории он
      рассчитан на `/opt/vkbot`; если проект лежит иначе, перед копированием:
      `sed 's#/opt/vkbot#/root/vkbot#g' deploy/vkbot-backup.service > /etc/systemd/system/vkbot-backup.service`.
      Каталог с базами обязан быть в `ReadWritePaths`: SQLite в WAL-режиме
      открывает базу на запись даже когда её только читают.
- [ ] Разовый прогон прошёл: `systemctl start vkbot-backup.service`,
      `journalctl -u vkbot-backup -n 30` — есть строка `integrity_check ok`.
- [ ] В `/var/backups/vkbot/<дата>/` лежат обе базы и `schedule_versions.tar.gz`
      (на последний опирается откат расписания).
- [ ] Глубина хранения устраивает: `BACKUP_KEEP_DAYS` в юните, по умолчанию 14 дней.
- [ ] Проверено восстановление: копия открывается и в ней есть данные.

## 7а. Мониторинг живости

- [ ] `curl -s https://<домен>/healthz` отдаёт `200` и `"status": "ok"`.
      `503` со `state: "never"` означает, что бот ещё ни разу не тикал —
      проверьте, что `vkbot` запущен.
- [ ] Внешняя проверка (uptime-монитор, cron с curl) дёргает `/healthz` и шлёт
      алерт на не-200. Это единственный способ заметить отказ, при котором
      процесс жив, а воркер встал: бот отвечает на сообщения, а напоминания и
      пуши о парах молча не приходят.

## 8. После запуска

- [ ] `journalctl -u vkbot -u vkpanel --since "1 hour ago" | grep -i error` — чисто.
- [ ] `/admin/audit` просмотрен: нет чужих `auth.rate_limited`, `vk.sign_invalid`.
- [ ] Известные ограничения приняты (см. ниже).

## Известные ограничения

* **Панель — один процесс.** Отложенные загрузки, прогресс рассылки и кэш `.ics`
  хранятся в памяти. Второй воркер сломает загрузку расписания.
* **Легаси `bot.py`** (Telegram) не нужен для работы продукта и по умолчанию не
  запускается. Он хранит пользовательские GPT-ключи в БД в открытом виде — если
  всё же поднимаете, учитывайте это. Там же `proxy_watchdog` завершает процесс
  после восьми ошибок соединения подряд и не сбрасывает счётчик; при пустом
  `TELEGRAM_PROXIES` ротировать нечего, так что под systemd с `Restart=always`
  сетевые сбои превратятся в цикл перезапусков.
* **Чётность недели** считается от ISO-номера недели (`vkbot/schedule/week.py`),
  а не от даты начала семестра. Сверьте с расписанием вуза: если «чёт»/«нечет»
  разошлись, инвертировать нужно ровно в одном этом месте.
